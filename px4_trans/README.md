# PX4 神经网络控制器移植与嵌入层

## 1. 项目定位

本目录用于完成开源 PX4 飞控的移植、裁剪与改造，并将训练完成的循环神经网络控制器部署到飞控 MCU。最终目标是以神经网络替代传统飞控中的姿态 **controller + control allocation** 链路：真实飞手直接控制上桨油门，网络接收飞手姿态命令、当前上桨油门、飞行器状态和必要历史信息，输出下桨电机与三路舵机的归一化指令。

本层位于训练系统与真实执行机构之间，重点解决的不是网络训练，而是以下工程问题：

- 将上层训练产物转换为可追踪、可复现的部署模型；
- 在 PX4 中建立稳定的神经网络控制器接口和调度链路；
- 在资源受限的 MCU 上实现低延迟、确定性的循环网络前向传播；
- 完成权重、代码和工作区的存储布局与链接配置；
- 验证桌面端、目标板与训练框架输出的一致性；
- 保留限幅、失效保护、传统控制器回退和人工接管能力。

上层总体方案见 [`../Docs/目标：使用循环神经网络替代传统飞控中的controller+alloc.txt`](../Docs/%E7%9B%AE%E6%A0%87%EF%BC%9A%E4%BD%BF%E7%94%A8%E5%BE%AA%E7%8E%AF%E7%A5%9E%E7%BB%8F%E7%BD%91%E7%BB%9C%E6%9B%BF%E4%BB%A3%E4%BC%A0%E7%BB%9F%E9%A3%9E%E6%8E%A7%E4%B8%AD%E7%9A%84controller%2Balloc.txt)。

> 当前基线：完整的 PX4 仓库以子模块形式位于 `px4/`，使用项目 fork
> `Ryan-5853/PX4-Autopilot` 的 `teleai/v1.16.2` 分支，基于 PX4
> `v1.16.2`。目标飞控板已经确定为 MicoAir H743 V2，项目固件 target 为
> `micoair_h743-v2_nncontrol`。2026-07-23 已使用 ARM GCC 10.3.1 完成
> NuttX 硬件固件全量编译验证。

## 2. 系统边界

### 2.1 本层输入

面向 PX4 的外部语义接口至少包含：

- 目标姿态；
- 当前飞手上桨油门；
- EKF 输出的实时姿态与角速度；
- 网络结构要求的其他观测量；
- 上一时刻 4 维策略动作；
- 循环网络隐藏状态，以及隐藏状态的复位信号。

按照当前训练方案，候选观测向量为 21 维：

| 信号 | 维度 | 说明 |
| --- | ---: | --- |
| 当前姿态四元数 | 4 | 约定分量顺序和坐标系 |
| 机体角速度 | 3 | 约定单位与坐标系 |
| 机体加速度 | 3 | 明确是否包含重力 |
| 两路电机转速 | 2 | 明确归一化或物理单位 |
| 目标姿态四元数 | 4 | 与当前姿态使用同一约定 |
| 当前上桨油门 | 1 | 飞手直接输入，`[0,1]` 映射到模型范围 |
| 上一时刻策略动作 | 4 | 下桨电机、三路舵机 |

实际部署前必须把输入顺序、单位、范围、坐标系、时间戳策略、归一化参数和异常值处理固化为一份机器可读的模型清单。训练端和固件端不得分别手工维护这些定义。

### 2.2 本层输出

网络输出 4 维归一化策略动作：

- 一路下桨电机指令；
- 三路舵机指令。

PX4 命令合成器把真实飞手的上桨油门放在执行器通道 0，再拼接网络的下桨电机和
三路舵机，形成 5 维执行器命令。网络不得覆盖上桨油门；切换、失效保护和人工接管
也必须保持该所有权边界。

输出进入硬件驱动前仍需经过确定性的安全后处理，包括有限值检查、限幅、变化率限制、解锁状态检查和失效保护。归一化区间及其到 PWM、DShot 或其他执行器协议的映射由板级执行器配置明确规定。

### 2.3 暂不属于本层的工作

- 真机参数辨识与动力学模型建立；
- PyTorch/TorchRL 仿真环境开发；
- 强化学习训练、专家策略合并和策略蒸馏；
- 飞行器机械结构、测试台和传感器硬件设计。

本层可以提供训练端所需的接口约束、量化约束和 MCU 性能反馈，但不在这里复制训练系统。

## 3. 目标运行链路

```text
目标姿态 ───┐
飞手上桨油门 ├─> 观测采集与时间对齐 ─> 预处理/归一化 ─> RNN 前向传播 ─> 4维策略动作
EKF/传感器 ──┤                                                               │
电机反馈 ────┘                                                               v
飞手上桨油门 ───────────────────────────────────────────────> 命令合成与安全后处理
                                                                             │
                                                                             v
                                                                   PX4 5维执行器输出
```

循环网络的隐藏状态属于飞控运行状态，必须明确其生命周期：

1. 上电、软件重启、模型切换和控制器启用时复位；
2. 未解锁期间保持复位，或按经过验证的预热策略更新；
3. 输入超时、姿态估计失效、数值异常或调度超期时失效；
4. 若采用“慢参数辨识网络 + 快控制网络”，持久化隐藏状态必须带模型版本、机体标识、校验和与有效性条件，禁止无条件加载旧状态。

## 4. PX4 集成原则

初期应尽量把改动限制在独立模块和清晰接口内，避免直接散改 PX4 核心代码。建议采用以下边界：

- **输入适配层**：订阅目标姿态、估计状态、电机反馈和安全状态等 uORB 主题，完成时间同步与有效性检查；
- **模型运行时**：只处理定长张量、隐藏状态和前向传播，不直接依赖 uORB、驱动或板级 API；
- **输出适配层**：发布动作或直接接入执行器链路，并执行限幅、失效保护与模式切换；
- **参数与命令层**：控制模型启用、隐藏状态复位、调试统计和传统控制器回退；
- **板级配置层**：放置内存区、链接脚本片段、编译选项、缓存策略和硬件相关优化。

集成时需要结合所选 PX4 版本核实实际 uORB 主题和 actuator pipeline。由于网络同时替代 controller 与 allocator，必须避免动作再次进入传统分配器，也不能绕过 PX4 的解锁、failsafe 和输出抑制机制。

建议在早期保留传统控制链路，通过明确的飞行模式或参数进行切换。切换只应在满足姿态估计有效、模型已初始化、推理周期正常等条件时发生；空中热切换是否允许，需要通过仿真、HIL 和受控真机测试单独论证。

## 5. 模型导出契约

训练端导出的不应只是一个权重文件，而应是一个完整、版本化的部署包。建议至少包含：

```text
model_package/
├── manifest.json          # 模型版本、结构、张量形状与数据类型
├── weights.*              # 浮点或量化后的权重
├── normalization.*        # 输入/输出缩放、零点和截断范围
├── test_vectors/          # 输入、初始隐藏状态和期望输出
├── export_report.*        # 算子、量化误差和导出工具版本
└── checksum.*             # 部署包完整性校验
```

`manifest` 至少固定以下内容：

- 网络类型、层数、激活函数和隐藏状态形状；
- 每个输入与输出的名称、顺序、单位、坐标系和合法范围；
- 权重、激活和累加器的数据类型；
- 对称/非对称、逐张量/逐通道等量化方案及参数；
- 隐藏状态的初始化方法；
- 训练代码版本、导出脚本版本和模型校验和；
- 一组覆盖正常、边界与饱和情况的黄金测试向量。

四元数必须特别注明 `wxyz` 或 `xyzw` 顺序、机体系/世界系方向、主动/被动旋转定义以及归一化规则。这类语义差异不会产生编译错误，却可能直接导致控制失效。

## 6. 推理实现路线

本项目允许并行评估多条实现路线，但所有实现必须满足同一 C ABI 和同一组黄金测试向量，从而可以替换而不改变 PX4 集成代码。

建议最小接口表达以下能力：

```c
int nn_controller_init(void);
void nn_controller_reset(void);
int nn_controller_step(const float *observation, float *action);
```

量化实现可以在内部使用定点张量，也可以增加显式定点接口；最终接口设计应在模型结构确定后冻结。禁止在实时循环中动态分配内存。

### 6.1 手写 C 前向传播

先实现结构简单、易审查的标量 C 参考版本，用于确认张量布局、门控公式、量化参数和隐藏状态更新顺序。它也是后续优化实现的差分测试基准。首版优先保证正确性和可测试性，再基于性能数据优化。

### 6.2 自动代码生成

可评估 STM32Cube.AI 等与目标芯片匹配的官方工具，将训练模型转换为 C 代码和运行时库。采用前需验证：

- 是否完整支持所选 GRU/RNN 算子和量化格式；
- 生成代码的 RAM、Flash 和最坏执行时间；
- 许可证与生成物是否适合随固件构建；
- 隐藏状态是否可显式复位、读取或注入；
- 生成结果是否能通过统一黄金向量测试。

### 6.3 CMSIS-DSP / CMSIS-NN 加速

对于 ARM Cortex-M 目标，可使用 CMSIS-DSP 或 CMSIS-NN 优化矩阵乘、激活与量化算子。应先用性能剖析确认热点，避免为了调用库而引入额外的数据重排开销。需要同时核对目标内核的 DSP、FPU、MVE/Helium 能力以及库版本。

### 6.4 定点化与 INT8 量化

量化目标是降低计算时间和存储占用，但循环网络对隐藏状态累计误差较敏感。除逐步输出误差外，还必须比较长序列运行后的隐藏状态漂移和闭环控制效果。必要时采用权重 INT8、隐藏状态/累加器更高精度的混合精度方案，而不是强制所有张量使用同一位宽。

### 6.5 手写汇编或编译器内建指令

只对已经确认的热点内核使用汇编、内联汇编或 SIMD intrinsic。优先保留可移植的 C 参考实现，并为优化内核提供目标板差分测试。直接生成整网汇编的维护与验证成本较高，应以实测结果证明其必要性。

## 7. 内存与链接布局

模型权重、运行时代码和工作区应按访问特征分别放置。若目标 MCU 具备 ITCM、DTCM、片上 SRAM、外部 Flash 或 Cache，可考虑：

- 高频推理代码放置在低延迟指令区；
- 热权重、隐藏状态和工作区放置在低延迟数据区；
- 冷权重或只读常量放置在合适的 Flash/只读区；
- DMA 使用的缓冲区遵守目标芯片的可访问范围和 Cache 一致性要求；
- 大对象使用静态分配，并通过链接期断言或构建报告检查越界。

链接脚本应以 PX4/NuttX 对目标板的现有脚本为基础，通过板级配置或独立 section 扩展。STM32CubeMX/STM32CubeIDE 生成的链接文件可以作为芯片内存布局参考，但不能未经核对直接覆盖 PX4 的启动、内存和 section 约定。

最终构建报告至少记录：

| 指标 | 内容 |
| --- | --- |
| Flash/ROM | 固件总量、模型权重、推理代码增量 |
| SRAM | 静态区、栈峰值、模型工作区、隐藏状态 |
| 特殊内存 | ITCM、DTCM、CCM 或外部内存占用 |
| 对齐 | 权重和 SIMD 数据的对齐要求 |
| 余量 | 各内存区剩余空间与安全裕量 |

## 8. 实时性目标

目标控制频率为 **500 Hz**，单控制周期约 **2 ms**。按总体方案：

- 推荐推理时间不超过周期的 30%，即约 **0.6 ms**；
- 最差推理时间不超过周期的 50%，即约 **1.0 ms**；
- 性能结论以目标板上的最坏情况测量为准，不能只使用桌面平均耗时；
- 测量应覆盖 Cache 冷启动、中断干扰、不同输入、隐藏状态长期运行和其他 PX4 任务负载；
- 记录平均值、P99、最大值、超期次数以及完整控制任务的端到端延迟。

若无法满足预算，应依次评估网络裁剪、低秩或稀疏结构、量化、算子融合、内存搬移、CMSIS 加速和热点内核优化。只有测量证明通用实现仍不足时，再扩大手写汇编范围。

## 9. 安全要求

神经网络输出不能被视为天然可信。进入真实执行器前至少落实：

- 检查输入时间戳、估计器健康状态和所有数值的有限性；
- 检查输出是否为有限值，并执行幅值和变化率限制；
- 监测推理超时、连续超期、隐藏状态异常和模型初始化失败；
- 明确定义上电、解锁、模式切换、通信丢失和 EKF 重置时的动作；
- 保留立即停机、人工接管和传统控制器回退路径；
- 为模型文件和持久化状态提供版本检查与完整性校验；
- 调试日志不得破坏 500 Hz 实时循环。

任何真机测试都应按照 SIL → HIL → 无桨台架 → 系留/保护装置 → 受控飞行的顺序逐级放开，并为每一级设置可量化的准入条件。

## 10. 验证策略

### 10.1 数值一致性

对同一模型、同一输入序列和同一初始隐藏状态，逐级比较：

1. PyTorch 浮点参考输出；
2. 导出后的桌面 C 参考实现；
3. 量化或 CMSIS 优化实现；
4. 目标 MCU 实际输出；
5. PX4 调度链路中的端到端输出。

测试不仅比较单步动作，还应连续运行足够长的序列，比较隐藏状态和输出误差随时间的累计情况。浮点实现使用明确的绝对/相对容差；定点实现使用由闭环仿真验证过的量化误差阈值。

### 10.2 功能与故障注入

至少覆盖：

- 零输入、边界输入、饱和输入和随机输入；
- NaN、Inf、过期数据、丢帧和时间戳跳变；
- 隐藏状态复位、模型重载和控制模式切换；
- 推理超时、任务阻塞和执行器反馈缺失；
- 长时间运行后的数值稳定性与内存稳定性。

### 10.3 闭环验证

数值一致不代表闭环稳定。每次改变模型结构、量化方案、编译器优化、算子实现或控制频率后，都需要重新运行仿真回归。HIL 和真机日志应能回放至桌面推理器，帮助区分模型问题、接口问题与实时调度问题。

## 11. 建议目录结构

PX4 源码与第一版部署工具引入后，可按实际构建系统调整为：

```text
px4_trans/
├── README.md
├── px4/                       # 固定版本的 PX4 源码或明确的子模块
├── model/
│   ├── manifest/              # 模型接口与版本信息
│   ├── generated/             # 由脚本生成的权重/代码，不手工修改
│   └── test_vectors/          # 黄金输入、状态与输出
├── runtime/
│   ├── reference/             # 可移植 C 参考实现
│   ├── optimized/             # CMSIS、定点或目标相关实现
│   └── include/               # 稳定的运行时接口
├── tools/
│   ├── export/                # 训练模型导出与量化脚本
│   └── benchmark/             # 桌面端和目标板性能工具
├── boards/                    # 板级链接、内存和编译配置
├── tests/                     # 数值一致性与故障注入测试
└── docs/                      # 接口、移植记录、测试报告和决策记录
```

生成文件必须能够由固定版本的脚本和工具重新生成。模型权重是否纳入 Git，应根据文件大小、更新频率和仓库策略决定；无论采用 Git、Git LFS 或外部制品库，都必须可由校验和唯一识别。

## 12. 实施阶段与验收标准

### 阶段 A：基线与接口冻结

- 选定 PX4 版本、目标板、编译器和基础固件配置；
- 明确 21 维输入、4 维策略输出和 5 维执行器命令的完整语义与所有权；
- 定义模型部署包、稳定 C ABI 和黄金测试格式；
- 在桌面端跑通手写 C 浮点参考实现。

**验收：** PyTorch 与 C 参考实现在长序列测试中满足约定误差，模型可重复导出。

### 阶段 B：PX4 最小集成

- 建立独立 PX4 模块、uORB 输入和执行器输出适配；
- 跑通隐藏状态复位、启停、调试统计和安全限幅；
- 保留传统控制路径和明确的回退机制。

**验收：** SIL 中以 500 Hz 稳定运行，接口、模式切换和故障处理符合预期。

### 阶段 C：MCU 部署与优化

- 比较手写 C、自动代码生成、CMSIS 和量化方案；
- 完成内存布局、链接配置和目标板性能测量；
- 固定最终实现及其工具版本。

**验收：** 目标 MCU 输出通过黄金测试，最坏推理时间与内存占用满足预算，无动态内存和长期运行漂移。

### 阶段 D：闭环与真机验证

- 完成 SIL/HIL 回归、故障注入和日志回放；
- 按安全阶梯进行无桨、系留和受控飞行测试；
- 将实测延迟、传感器误差和执行器动态反馈给训练环境。

**验收：** 达成总体项目定义的 MCU 实时推理和真机稳定控制 checkpoint。

## 13. 待确定事项

以下事项会直接影响移植方案，应在开始编码前或基线阶段尽快确定：

- 目标飞控板、具体 MCU、主频、Flash/SRAM/TCM 容量；
- PX4 基线版本、NuttX 版本和是否维护长期补丁集；
- 执行器硬件协议、输出范围、更新率与反馈来源；
- 网络最终结构、参数量、激活函数和隐藏状态规模；
- 浮点、INT8 或混合精度部署策略；
- EKF 输出作为主要观测，还是后续直接引入 IMU 原始观测；
- 传统控制器回退、模式切换与真机测试的安全规则；
- STM32Cube.AI、CMSIS 或其他工具的版本与许可证约束。

这些决策应记录在 `docs/` 下，并与模型清单、固件版本和测试报告建立对应关系，确保每次飞行所使用的软件与模型均可追溯。

## 14. PX4 v1.16.2 / MicoAir H743 V2 编译指南

本项目只使用以下硬件固件 target：

```text
micoair_h743-v2_nncontrol
```

该 target 包含传感器、EKF2、日志、遥控输入、Commander 和安全保护，以及项目自定义的
`nn_control` 模块；传统 PX4 多旋翼/固定翼控制器、Flight Mode Manager 和 Control
Allocator 均不参与构建。不要再使用 `micoair_h743-v2_default` 或通用 Pixhawk target
编译本项目固件。

### 14.1 检查源码版本与子模块

从大仓库根目录进入 PX4 子模块：

```bash
cd px4

git describe --tags --always --dirty
git branch --show-current
git status --short
git submodule status --recursive
```

当前版本应以 `v1.16.2` 为基线，开发分支为 `teleai/v1.16.2`。`dirty` 表示本地包含本项目
尚未提交的板级配置或控制器代码，并不等于版本错误。

若递归子模块尚未检出，执行：

```bash
git submodule sync --recursive
git submodule update --init --recursive
```

### 14.2 准备独立 Python 环境

不要让当前 Conda 环境中的 Python 3.13 参与 PX4 构建。项目使用仓库内的 Python 3.10
虚拟环境：

```bash
cd px4

python3.10 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r Tools/setup/requirements.txt ninja "setuptools<81"
```

`setuptools<81` 用于保留 PX4 v1.16.2 的 DroneCAN DSDL 编译器需要的
`pkg_resources`。验证关键 Python 依赖：

```bash
.venv/bin/python --version
.venv/bin/python -c 'import menuconfig, kconfiglib, pkg_resources; print("PX4 Python dependencies OK")'
.venv/bin/ninja --version
```

再确认 ARM 交叉编译器：

```bash
arm-none-eabi-gcc --version
```

若系统没有 ARM 工具链，可在 PX4 仓库中运行：

```bash
bash ./Tools/setup/ubuntu.sh --no-sim-tools
```

该安装脚本会使用系统包管理器、网络和 `sudo`。

### 14.3 编译神经网络控制器固件

在 `px4/` 目录中执行以下完整命令：

```bash
env \
  CCACHE_DISABLE=1 \
  MAKEFLAGS= \
  PATH="$PWD/.venv/bin:$PATH" \
  PYTHON_EXECUTABLE="$PWD/.venv/bin/python" \
  make micoair_h743-v2_nncontrol
```

这里有三项必须保留：

- `PATH` 和 `PYTHON_EXECUTABLE` 强制 CMake 使用仓库内的 Python 3.10 环境；
- `MAKEFLAGS=` 清除外层 Make jobserver 参数，避免 Ninja 报
  `Could not initialize jobserver: Invalid file descriptors`；
- 不在 `make` 后添加外层 `-j"$(nproc)"`，Ninja 会自行进行并行构建。

编译成功后固件位于：

```text
build/micoair_h743-v2_nncontrol/micoair_h743-v2_nncontrol.px4
```

2026-07-23 的已验证结果为：

```text
FLASH:     1046448 B / 1792 KB    57.03%
AXI_SRAM:    50696 B / 512 KB      9.67%
```

每次加入模型权重、推理运行时或新的驱动后，都必须重新检查链接器输出中的 Flash 和
RAM 占用，不能只检查是否生成了 `.px4` 文件。

### 14.4 增量编译、清理与上传

源码修改后，重复第 14.3 节的完整命令即可增量编译。

确实需要清理全部 PX4 构建产物时，在 `px4/` 中执行：

```bash
make clean
```

连接 MicoAir H743 V2、进入 Bootloader 后，可使用同一环境直接编译并上传：

```bash
env \
  CCACHE_DISABLE=1 \
  MAKEFLAGS= \
  PATH="$PWD/.venv/bin:$PATH" \
  PYTHON_EXECUTABLE="$PWD/.venv/bin/python" \
  make micoair_h743-v2_nncontrol upload
```

也可以在 QGroundControl 中选择“自定义固件”，手动上传：

```text
build/micoair_h743-v2_nncontrol/micoair_h743-v2_nncontrol.px4
```

### 14.5 烧录后的模块检查

当前 `nn_control` 已编入固件，但尚未设置为开机自动启动。进入 NSH 后执行：

```text
nn_control start
nn_control status
```

检查输入和执行器主题：

```text
listener vehicle_attitude
listener vehicle_angular_velocity
listener vehicle_acceleration
listener vehicle_local_position
listener manual_control_setpoint
listener actuator_motors
listener actuator_servos
```

当前神经网络接口仍是安全桩，`NeuralNetworkInterface::run()` 默认返回 `false`，所以
`actuator_motors` 和 `actuator_servos` 应显示 `NaN` 安全输出。接入并验证真实模型前，
不得通过临时常量或无条件 `return true` 绕过该保护。

### 14.6 常见构建错误

| 提示或错误 | 原因 | 处理方式 |
| --- | --- | --- |
| `No module named 'menuconfig'` | CMake 使用了 Conda 或系统 Python | 使用第 14.3 节的完整命令，并在 `.venv` 中安装 requirements |
| `kconfiglib is not installed` | 当前构建 Python 缺少 Kconfig 依赖 | 用 `.venv/bin/python` 安装 `Tools/setup/requirements.txt` |
| `No module named 'pkg_resources'` | 虚拟环境缺少兼容的 setuptools | 执行 `.venv/bin/python -m pip install "setuptools<81"` |
| `Could not initialize jobserver: Invalid file descriptors` | 外层 `make -j` 参数被传给 Ninja | 去掉 `-j"$(nproc)"` 并设置 `MAKEFLAGS=` |
| `arm-none-eabi-gcc: command not found` | ARM/NuttX 工具链未安装 | 运行 `Tools/setup/ubuntu.sh --no-sim-tools` |
| `BOARD_UAVCAN_INTERFACES ... got the value ''` | 基础板声明 UAVCAN 接口，但裁剪配置关闭了 UAVCAN | 当前配置中的预期警告，不影响固件生成 |

排错时优先处理日志中的第一个致命错误。CMake 配置失败后出现的“构建目录不存在”等信息
通常只是连锁错误。

### 14.7 可复现性与安全注意事项

- 提交或发布前记录 PX4 commit、`git describe`、编译器版本、target 和固件校验和；
- 固定主仓库和所有递归子模块的 commit，不要无记录地更新子模块；
- 不提交 `build/`、`.venv/`、日志、模型缓存或编译缓存；
- 始终显式指定 `.venv`，不要依赖当前终端碰巧激活的 Conda 环境；
- `nn_control` 当前直接发布 `actuator_motors` 和 `actuator_servos`，不会经过 Control
  Allocator；
- 接入真实模型后，必须重新完成无桨、台架、故障注入、SIL/HIL 和执行器映射验证；
- 在模型、输出映射和失效保护全部验证完成前，不得进行带桨测试。
