# PX4 神经网络控制器移植与嵌入层

## 1. 项目定位

本目录用于完成开源 PX4 飞控的移植、裁剪与改造，并将训练完成的循环神经网络控制器部署到飞控 MCU。最终目标是以神经网络替代传统飞控中的 **controller + control allocation** 链路：网络接收目标姿态、飞行器状态和必要的历史信息，直接输出两路电机与三路舵机的归一化指令。

本层位于训练系统与真实执行机构之间，重点解决的不是网络训练，而是以下工程问题：

- 将上层训练产物转换为可追踪、可复现的部署模型；
- 在 PX4 中建立稳定的神经网络控制器接口和调度链路；
- 在资源受限的 MCU 上实现低延迟、确定性的循环网络前向传播；
- 完成权重、代码和工作区的存储布局与链接配置；
- 验证桌面端、目标板与训练框架输出的一致性；
- 保留限幅、失效保护、传统控制器回退和人工接管能力。

上层总体方案见 [`../Docs/目标：使用循环神经网络替代传统飞控中的controller+alloc.txt`](../Docs/%E7%9B%AE%E6%A0%87%EF%BC%9A%E4%BD%BF%E7%94%A8%E5%BE%AA%E7%8E%AF%E7%A5%9E%E7%BB%8F%E7%BD%91%E7%BB%9C%E6%9B%BF%E4%BB%A3%E4%BC%A0%E7%BB%9F%E9%A3%9E%E6%8E%A7%E4%B8%AD%E7%9A%84controller%2Balloc.txt)。

> 当前状态：本目录仅建立嵌入层设计说明，尚未引入 PX4 源码、板级配置或模型文件。具体目标 MCU、PX4 版本和工具链确定后，应将它们固定在版本记录中。

## 2. 系统边界

### 2.1 本层输入

面向 PX4 的外部语义接口至少包含：

- 目标姿态；
- EKF 输出的实时姿态与角速度；
- 网络结构要求的其他观测量；
- 上一时刻动作；
- 循环网络隐藏状态，以及隐藏状态的复位信号。

按照当前训练方案，候选观测向量为 21 维：

| 信号 | 维度 | 说明 |
| --- | ---: | --- |
| 当前姿态四元数 | 4 | 约定分量顺序和坐标系 |
| 机体角速度 | 3 | 约定单位与坐标系 |
| 机体加速度 | 3 | 明确是否包含重力 |
| 两路电机转速 | 2 | 明确归一化或物理单位 |
| 目标姿态四元数 | 4 | 与当前姿态使用同一约定 |
| 上一时刻动作 | 5 | 两路电机、三路舵机 |

实际部署前必须把输入顺序、单位、范围、坐标系、时间戳策略、归一化参数和异常值处理固化为一份机器可读的模型清单。训练端和固件端不得分别手工维护这些定义。

### 2.2 本层输出

网络输出 5 维归一化动作：

- 两路电机指令；
- 三路舵机指令。

输出进入硬件驱动前仍需经过确定性的安全后处理，包括有限值检查、限幅、变化率限制、解锁状态检查和失效保护。归一化区间及其到 PWM、DShot 或其他执行器协议的映射由板级执行器配置明确规定。

### 2.3 暂不属于本层的工作

- 真机参数辨识与动力学模型建立；
- PyTorch/TorchRL 仿真环境开发；
- 强化学习训练、专家策略合并和策略蒸馏；
- 飞行器机械结构、测试台和传感器硬件设计。

本层可以提供训练端所需的接口约束、量化约束和 MCU 性能反馈，但不在这里复制训练系统。

## 3. 目标运行链路

```text
目标姿态 ─┐
          ├─> 观测采集与时间对齐 ─> 预处理/归一化 ─> RNN 前向传播
EKF/传感器 ┤                                          │
电机反馈 ──┘                                          v
                                         安全后处理与动作限幅
                                                    │
                                                    v
                                          PX4 执行器输出驱动
```

循环网络的隐藏状态属于飞控运行状态，必须明确其生命周期：

1. 上电、软件重启、模型切换和控制器启用时复位；
2. 未解锁期间保持复位，或按经过验证的预热策略更新；
3. 输入超时、姿态估计失效、数值异常或调度超期时失效；
4. 若采用“慢参数辨识网络 + 快控制网络”，持久化隐藏状态必须带模型版本、机体标识、校验和与有效性条件，禁止无条件加载旧状态。

## 4. PX4 集成原则

初期应尽量把改动限制在独立模块和清晰接口内，避免直接散改 PX4 核心代码。建议采用以下边界：

- **输入适配层**：订阅目标姿态、估计状态、电机反馈和安全状态等 uORB 主题，完成时间同步与有效性检查；
- **模型运行时**：只处理定长张量、隐藏状态和前向传播，不直接依赖 uORB、驱动或板级 API；
- **输出适配层**：发布动作或直接接入执行器链路，并执行限幅、失效保护与模式切换；
- **参数与命令层**：控制模型启用、隐藏状态复位、调试统计和传统控制器回退；
- **板级配置层**：放置内存区、链接脚本片段、编译选项、缓存策略和硬件相关优化。

集成时需要结合所选 PX4 版本核实实际 uORB 主题和 actuator pipeline。由于网络同时替代 controller 与 allocator，必须避免动作再次进入传统分配器，也不能绕过 PX4 的解锁、failsafe 和输出抑制机制。

建议在早期保留传统控制链路，通过明确的飞行模式或参数进行切换。切换只应在满足姿态估计有效、模型已初始化、推理周期正常等条件时发生；空中热切换是否允许，需要通过仿真、HIL 和受控真机测试单独论证。

## 5. 模型导出契约

训练端导出的不应只是一个权重文件，而应是一个完整、版本化的部署包。建议至少包含：

```text
model_package/
├── manifest.json          # 模型版本、结构、张量形状与数据类型
├── weights.*              # 浮点或量化后的权重
├── normalization.*        # 输入/输出缩放、零点和截断范围
├── test_vectors/          # 输入、初始隐藏状态和期望输出
├── export_report.*        # 算子、量化误差和导出工具版本
└── checksum.*             # 部署包完整性校验
```

`manifest` 至少固定以下内容：

- 网络类型、层数、激活函数和隐藏状态形状；
- 每个输入与输出的名称、顺序、单位、坐标系和合法范围；
- 权重、激活和累加器的数据类型；
- 对称/非对称、逐张量/逐通道等量化方案及参数；
- 隐藏状态的初始化方法；
- 训练代码版本、导出脚本版本和模型校验和；
- 一组覆盖正常、边界与饱和情况的黄金测试向量。

四元数必须特别注明 `wxyz` 或 `xyzw` 顺序、机体系/世界系方向、主动/被动旋转定义以及归一化规则。这类语义差异不会产生编译错误，却可能直接导致控制失效。

## 6. 推理实现路线

本项目允许并行评估多条实现路线，但所有实现必须满足同一 C ABI 和同一组黄金测试向量，从而可以替换而不改变 PX4 集成代码。

建议最小接口表达以下能力：

```c
int nn_controller_init(void);
void nn_controller_reset(void);
int nn_controller_step(const float *observation, float *action);
```

量化实现可以在内部使用定点张量，也可以增加显式定点接口；最终接口设计应在模型结构确定后冻结。禁止在实时循环中动态分配内存。

### 6.1 手写 C 前向传播

先实现结构简单、易审查的标量 C 参考版本，用于确认张量布局、门控公式、量化参数和隐藏状态更新顺序。它也是后续优化实现的差分测试基准。首版优先保证正确性和可测试性，再基于性能数据优化。

### 6.2 自动代码生成

可评估 STM32Cube.AI 等与目标芯片匹配的官方工具，将训练模型转换为 C 代码和运行时库。采用前需验证：

- 是否完整支持所选 GRU/RNN 算子和量化格式；
- 生成代码的 RAM、Flash 和最坏执行时间；
- 许可证与生成物是否适合随固件构建；
- 隐藏状态是否可显式复位、读取或注入；
- 生成结果是否能通过统一黄金向量测试。

### 6.3 CMSIS-DSP / CMSIS-NN 加速

对于 ARM Cortex-M 目标，可使用 CMSIS-DSP 或 CMSIS-NN 优化矩阵乘、激活与量化算子。应先用性能剖析确认热点，避免为了调用库而引入额外的数据重排开销。需要同时核对目标内核的 DSP、FPU、MVE/Helium 能力以及库版本。

### 6.4 定点化与 INT8 量化

量化目标是降低计算时间和存储占用，但循环网络对隐藏状态累计误差较敏感。除逐步输出误差外，还必须比较长序列运行后的隐藏状态漂移和闭环控制效果。必要时采用权重 INT8、隐藏状态/累加器更高精度的混合精度方案，而不是强制所有张量使用同一位宽。

### 6.5 手写汇编或编译器内建指令

只对已经确认的热点内核使用汇编、内联汇编或 SIMD intrinsic。优先保留可移植的 C 参考实现，并为优化内核提供目标板差分测试。直接生成整网汇编的维护与验证成本较高，应以实测结果证明其必要性。

## 7. 内存与链接布局

模型权重、运行时代码和工作区应按访问特征分别放置。若目标 MCU 具备 ITCM、DTCM、片上 SRAM、外部 Flash 或 Cache，可考虑：

- 高频推理代码放置在低延迟指令区；
- 热权重、隐藏状态和工作区放置在低延迟数据区；
- 冷权重或只读常量放置在合适的 Flash/只读区；
- DMA 使用的缓冲区遵守目标芯片的可访问范围和 Cache 一致性要求；
- 大对象使用静态分配，并通过链接期断言或构建报告检查越界。

链接脚本应以 PX4/NuttX 对目标板的现有脚本为基础，通过板级配置或独立 section 扩展。STM32CubeMX/STM32CubeIDE 生成的链接文件可以作为芯片内存布局参考，但不能未经核对直接覆盖 PX4 的启动、内存和 section 约定。

最终构建报告至少记录：

| 指标 | 内容 |
| --- | --- |
| Flash/ROM | 固件总量、模型权重、推理代码增量 |
| SRAM | 静态区、栈峰值、模型工作区、隐藏状态 |
| 特殊内存 | ITCM、DTCM、CCM 或外部内存占用 |
| 对齐 | 权重和 SIMD 数据的对齐要求 |
| 余量 | 各内存区剩余空间与安全裕量 |

## 8. 实时性目标

目标控制频率为 **500 Hz**，单控制周期约 **2 ms**。按总体方案：

- 推荐推理时间不超过周期的 30%，即约 **0.6 ms**；
- 最差推理时间不超过周期的 50%，即约 **1.0 ms**；
- 性能结论以目标板上的最坏情况测量为准，不能只使用桌面平均耗时；
- 测量应覆盖 Cache 冷启动、中断干扰、不同输入、隐藏状态长期运行和其他 PX4 任务负载；
- 记录平均值、P99、最大值、超期次数以及完整控制任务的端到端延迟。

若无法满足预算，应依次评估网络裁剪、低秩或稀疏结构、量化、算子融合、内存搬移、CMSIS 加速和热点内核优化。只有测量证明通用实现仍不足时，再扩大手写汇编范围。

## 9. 安全要求

神经网络输出不能被视为天然可信。进入真实执行器前至少落实：

- 检查输入时间戳、估计器健康状态和所有数值的有限性；
- 检查输出是否为有限值，并执行幅值和变化率限制；
- 监测推理超时、连续超期、隐藏状态异常和模型初始化失败；
- 明确定义上电、解锁、模式切换、通信丢失和 EKF 重置时的动作；
- 保留立即停机、人工接管和传统控制器回退路径；
- 为模型文件和持久化状态提供版本检查与完整性校验；
- 调试日志不得破坏 500 Hz 实时循环。

任何真机测试都应按照 SIL → HIL → 无桨台架 → 系留/保护装置 → 受控飞行的顺序逐级放开，并为每一级设置可量化的准入条件。

## 10. 验证策略

### 10.1 数值一致性

对同一模型、同一输入序列和同一初始隐藏状态，逐级比较：

1. PyTorch 浮点参考输出；
2. 导出后的桌面 C 参考实现；
3. 量化或 CMSIS 优化实现；
4. 目标 MCU 实际输出；
5. PX4 调度链路中的端到端输出。

测试不仅比较单步动作，还应连续运行足够长的序列，比较隐藏状态和输出误差随时间的累计情况。浮点实现使用明确的绝对/相对容差；定点实现使用由闭环仿真验证过的量化误差阈值。

### 10.2 功能与故障注入

至少覆盖：

- 零输入、边界输入、饱和输入和随机输入；
- NaN、Inf、过期数据、丢帧和时间戳跳变；
- 隐藏状态复位、模型重载和控制模式切换；
- 推理超时、任务阻塞和执行器反馈缺失；
- 长时间运行后的数值稳定性与内存稳定性。

### 10.3 闭环验证

数值一致不代表闭环稳定。每次改变模型结构、量化方案、编译器优化、算子实现或控制频率后，都需要重新运行仿真回归。HIL 和真机日志应能回放至桌面推理器，帮助区分模型问题、接口问题与实时调度问题。

## 11. 建议目录结构

PX4 源码与第一版部署工具引入后，可按实际构建系统调整为：

```text
px4_trans/
├── README.md
├── px4/                       # 固定版本的 PX4 源码或明确的子模块
├── model/
│   ├── manifest/              # 模型接口与版本信息
│   ├── generated/             # 由脚本生成的权重/代码，不手工修改
│   └── test_vectors/          # 黄金输入、状态与输出
├── runtime/
│   ├── reference/             # 可移植 C 参考实现
│   ├── optimized/             # CMSIS、定点或目标相关实现
│   └── include/               # 稳定的运行时接口
├── tools/
│   ├── export/                # 训练模型导出与量化脚本
│   └── benchmark/             # 桌面端和目标板性能工具
├── boards/                    # 板级链接、内存和编译配置
├── tests/                     # 数值一致性与故障注入测试
└── docs/                      # 接口、移植记录、测试报告和决策记录
```

生成文件必须能够由固定版本的脚本和工具重新生成。模型权重是否纳入 Git，应根据文件大小、更新频率和仓库策略决定；无论采用 Git、Git LFS 或外部制品库，都必须可由校验和唯一识别。

## 12. 实施阶段与验收标准

### 阶段 A：基线与接口冻结

- 选定 PX4 版本、目标板、编译器和基础固件配置；
- 明确 21 维输入与 5 维输出的完整语义；
- 定义模型部署包、稳定 C ABI 和黄金测试格式；
- 在桌面端跑通手写 C 浮点参考实现。

**验收：** PyTorch 与 C 参考实现在长序列测试中满足约定误差，模型可重复导出。

### 阶段 B：PX4 最小集成

- 建立独立 PX4 模块、uORB 输入和执行器输出适配；
- 跑通隐藏状态复位、启停、调试统计和安全限幅；
- 保留传统控制路径和明确的回退机制。

**验收：** SIL 中以 500 Hz 稳定运行，接口、模式切换和故障处理符合预期。

### 阶段 C：MCU 部署与优化

- 比较手写 C、自动代码生成、CMSIS 和量化方案；
- 完成内存布局、链接配置和目标板性能测量；
- 固定最终实现及其工具版本。

**验收：** 目标 MCU 输出通过黄金测试，最坏推理时间与内存占用满足预算，无动态内存和长期运行漂移。

### 阶段 D：闭环与真机验证

- 完成 SIL/HIL 回归、故障注入和日志回放；
- 按安全阶梯进行无桨、系留和受控飞行测试；
- 将实测延迟、传感器误差和执行器动态反馈给训练环境。

**验收：** 达成总体项目定义的 MCU 实时推理和真机稳定控制 checkpoint。

## 13. 待确定事项

以下事项会直接影响移植方案，应在开始编码前或基线阶段尽快确定：

- 目标飞控板、具体 MCU、主频、Flash/SRAM/TCM 容量；
- PX4 基线版本、NuttX 版本和是否维护长期补丁集；
- 执行器硬件协议、输出范围、更新率与反馈来源；
- 网络最终结构、参数量、激活函数和隐藏状态规模；
- 浮点、INT8 或混合精度部署策略；
- EKF 输出作为主要观测，还是后续直接引入 IMU 原始观测；
- 传统控制器回退、模式切换与真机测试的安全规则；
- STM32Cube.AI、CMSIS 或其他工具的版本与许可证约束。

这些决策应记录在 `docs/` 下，并与模型清单、固件版本和测试报告建立对应关系，确保每次飞行所使用的软件与模型均可追溯。
